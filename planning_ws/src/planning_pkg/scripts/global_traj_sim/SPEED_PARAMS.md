# CSV 속도는 누가 정하는가 — build_map.py 속도 파라미터 정리

> 2026-08-09 작성. 기준 맵 `my_track0808`, 기준 백 `rosbag0808/run_0808_222208`.
> 코드는 [`build_map.py`](build_map.py), 상수 근거는 그 파일의 설정 블록 주석에 있다.

**한 줄 요약: "속도가 안 나온다" 싶을 때 `V_MAX` 와 `MU_PROFILE` 은 보지 마라.
`LAT_ERR_CORNER_S` 와 트랙 폭이다.**

## 0. 왜 이 문서가 필요한가

`my_track0808` CSV 를 만들 때 `V_MAX = 7.0` 인데 실제 프로파일 최고속은 6.65,
평균은 4.07 m/s 다. `V_MAX` 를 9.0 으로 올려도 랩타임이 **소수점 둘째 자리까지
똑같다**. 같은 함정을 반복해서 밟았기 때문에 근거를 한 곳에 모은다.

## 1. 파라미터는 세 부류다 — 섞어서 보면 안 된다

| 부류 | 무엇을 바꾸나 | 해당 상수 |
|---|---|---|
| **(A) 라인의 모양** | CSV 의 `x` `y` `psi` `kappa` | `SAFE_DIST_*`, `RACELINE`, `SP_CURV_W`, `INFIELD_FILL_M`, `MIN_ISLAND_M2` |
| **(B) 라인 위의 속도** | CSV 의 `vx` `ax` **만** | `V_MAX`, `MU_PROFILE`, `LAT_ERR_*`, `A_*_CORNER`, `WIDTH_CAP_SMOOTH_*`, `LONGITUDINAL_SMOOTH_*` |
| **(C) 검증·보고용** | 아무것도 안 만든다 | `MU`, `MARGIN`, `CAR_HALF_*`, `JERK_REPORT_LIMIT` |

> **"레이스라인은 그대로 두고 속도만 올리고 싶다" = (B) 만 만지면 된다.**
> 실제로 `--lat-err-corner` 만 바꿔 재생성하면
> `s / x / y / d_left / d_right / psi / kappa` 열이 **maxdiff 0.000e+00** 으로
> 비트 단위 동일하고 `vx / ax` 만 바뀐다 (2026-08-09 확인).

## 2. 속도가 정해지는 3단계

### 1단계 — 점마다 상한 3개를 계산해 그중 **최소값**을 쓴다

```
곡률 상한 = sqrt(MU_PROFILE × g / |kappa|)     ← 타이어가 안 미끄러지는 물리 한계
폭   상한 = (벽까지 여유 − 차 반폭) / lat_err_slope   ← 벽에 안 닿는 기하 한계
V_MAX     = 그냥 상수 천장
```

### 2단계 — `velocity_profile()` 이 상한 사이를 가감속 램프로 잇는다

한 점이 3.0 m/s 로 묶이면 그 앞은 감속으로, 뒤는 가속으로 이어야 한다.
그래서 **상한에 실제로 붙어 있는 점보다 램프 위에 있는 점이 훨씬 많다.**

| my_track0808 (323 점) | |
|---|---|
| 가감속 램프 위 | **299 점 (92.6%)** |
| 정적 상한에 붙음 | 24 점 (7.4%) |

→ 어느 한 점의 상한을 낮추면 **그 주변 수 미터가 통째로 느려진다.**
→ 천장(`V_MAX`)을 올려도 아무 일이 안 일어나는 이유가 이것이다.

램프 기울기는 `A_ACC_MAX` / `A_DEC_PLANNED` (직선, 4.5 / 2.38 m/s²) 와
`A_ACC_CORNER` / `A_DEC_CORNER` (코너, 1.6 / 1.6) 가 정한다.

### 3단계 — `smooth_longitudinal()` 이 톱니를 깎는다

2 패스, 창 0.55 m (차 전장). **속도를 낮추기만 한다** — 안전 검증을 우회하지 않는다.

## 3. `lat_err_slope` = `--lat-err-corner` / `--lat-err-straight`

단위가 **초 [s]** 라서 헷갈리는데 뜻은 한 줄이다.

> ### 속도 1 m/s 당 차가 라인 밖으로 몇 m 밀려나는가

```
예상 횡추적오차 [m] = lat_err_slope [s] × 속도 [m/s]
```

실차는 계획된 라인을 정확히 밟지 못한다. pure pursuit 의 lookahead 가 코너
바깥을 당기기 때문에 바깥으로 밀리고, 빠를수록 많이 밀린다.
**밀려난 만큼은 벽 여유를 까먹는다.** 뒤집으면 "벽에 안 닿고 낼 수 있는 최대
속도"가 나온다:

```
폭 상한 = (벽까지 여유 − 차 반폭 0.15) ÷ lat_err_slope
```

| 벽 여유 | 쓸 수 있는 여유 | slope 0.117 → | slope 0.095 → |
|---|---|---|---|
| 0.42 m | 0.27 m | **2.3 m/s** | **2.9 m/s** |

즉 이 값은 **"차가 얼마나 못 미더운가"를 숫자로 적은 것**이고, 낮출수록 빨라진다.
반대로 실제보다 낮게 잡으면 계획이 벽 여유가 실제보다 많이 남을 거라고 착각해서
코너에서 벽에 붙는다. **안전 마진 그 자체다** — 상상해서 정하면 안 되고,
실차 백에서 재는 값이다 (§7 절차 참조).

### 왜 직선/코너 두 개인가

실차 오차는 **속도가 아니라 직전 곡률에 지배**된다. 직선에서는 잘 따라가고,
코너를 **빠져나온 직후**에 제일 많이 밀린다 (조향을 풀면서 가속하는 구간).
하나로 합치면 코너 기준으로 잡아야 안전한데, 그러면 직선까지 3.5 m/s 로 깎여
`v_max` 가 6.00 → 4.26 으로 무너진다.

| 관련 상수 | 뜻 |
|---|---|
| `LAT_ERR_STRAIGHT_S` = 0.030 | 직선 기울기 |
| `LAT_ERR_CORNER_S` = **0.090** | 코너 기울기 (2026-08-09 0.117 에서 내림, §7) |
| `LAT_ERR_KAPPA_LOW/HIGH` = 0.05 / 0.30 | 직선/코너 판정 곡률 경계 (그 사이는 선형 보간) |
| `LAT_ERR_KAPPA_WINDOW_M` = 2.0 | '직전 곡률'을 몇 m 뒤까지 볼지 → **§3.1** |
| `LAT_ERR_EXIT_DECAY_M` = 0.8 | 코너 탈출 후 얼마나 빨리 직선 취급으로 돌아올지 → **§3.1** |
| `WIDTH_CAP_SMOOTH_M` / `_MAX_GAIN` = 0.55 / 1.20 | 0.1 m 격자 노이즈로 생긴 V자 노치를 차 전장 창으로 평활 |

### 3.1 `LAT_ERR_KAPPA_WINDOW_M` 과 `LAT_ERR_EXIT_DECAY_M`

이 둘은 **"지금 이 점을 직선으로 볼 것인가 코너로 볼 것인가"** 를 정한다.
`recent_max_kappa()` 한 함수의 두 손잡이라서 따로 이해하면 안 된다.

```
kr[i] = max over j ( |kappa[i−j]| × exp(−j·ds / EXIT_DECAY_M) )
                     └ 뒤로 j 칸 ┘   └ 거리에 따른 할인 ┘
        j = 0 … KAPPA_WINDOW_M / ds        (ds = 0.1 m → 2.0 m = 20 칸)
```

**왜 현재 곡률을 안 쓰나.** 횡오차가 최대가 되는 곳은 코너 *안*이 아니라
코너를 **빠져나온 직후**다 — 조향을 풀면서 가속하는 구간이라 lookahead 가
라인 바깥으로 끌린다. 그런데 코너 출구의 `kappa` 는 이미 0 에 가깝다.
현재 곡률로 판정하면 **오차가 제일 큰 지점을 '직선'으로 오인**한다.
그래서 "방금 지나온 곡률"을 본다.

- **`WINDOW_M` (2.0 m)** = 몇 m 뒤까지 기억할지 (하드 컷오프)
- **`EXIT_DECAY_M` (0.8 m)** = 그 기억을 거리에 따라 얼마나 빨리 잊을지 (시정수)

`j=0` 의 가중치는 항상 1 이므로 **코너 진입과 코너 안의 보수성은 손대지 않고,
탈출에서만 상한이 풀린다.**

| 뒤로 | decay 0.4 | **decay 0.8 (현행)** | decay 1.5 | `None` (옛 동작) |
|---|---|---|---|---|
| 0.0 m | 1.000 | 1.000 | 1.000 | 1.000 |
| 0.4 m | 0.368 | 0.607 | 0.766 | 1.000 |
| 0.8 m | 0.135 | 0.368 | 0.587 | 1.000 |
| 2.0 m | 0.007 | **0.082** | 0.264 | 1.000 |

#### 실제로 뭘 고쳤나 — 헤어핀(s 19~24.7) 탈출부

| s | 실제 \|κ\| | 여유 | decay 0.8 → kr / 폭상한 | `None` → kr / 폭상한 |
|---|---|---|---|---|
| 25.4 | 0.246 | 0.38 | 0.246 / **3.82** | 0.529 / 3.21 |
| 26.0 | 0.172 | 0.33 | 0.172 / **4.48** | 0.441 / 2.78 ← 1.7 m/s 차 |
| 26.6 | 0.089 | 0.35 | 0.091 / **7.00** | 0.343 / 2.99 |
| 27.2 | 0.026 | 0.33 | 0.043 / **7.00** | 0.270 / 3.05 |

`None`(hard rolling-max)은 곡률이 이미 0.026 인 s 27.2 에서도 헤어핀의 0.27 을
그대로 물고 있어서 상한을 3 m/s 에 묶는다. **실차에서 느낀 "풀악셀이 늦다"가
정확히 이것이다.** 지수 가중이 이걸 없앴다 (2026-08-08).

#### ⚠️ 알아둘 것 두 가지

**① `EXIT_DECAY_M` 은 사실상 on/off 스위치다.** 값을 고르는 게 아니다.

| 설정 | 랩 | v_max |
|---|---|---|
| decay 0.4 / **0.8** / 1.5 | 7.59 s | 6.77 | ← 전부 동일 |
| decay `None` (옛 동작) | 7.78 s | 6.38 | **+0.19 s, 최고속 −0.39** |

0.4 와 1.5 가 같은 이유는, 그 차이가 나는 구간은 이미 곡률 상한이나 이웃의
가감속 램프가 더 낮아서 폭 상한이 아무 것도 안 물기 때문이다.
→ **켜져 있기만 하면 된다. `None` 으로 되돌리면 0.19 s 를 그냥 잃는다.**

**② decay 가 켜져 있으면 `WINDOW_M` 은 아무 것도 안 한다.**
지수 가중이 창 끝에 닿기 훨씬 전에 기여를 죽이기 때문이다 — decay 0.8 에서
2.0 m 뒤 가중은 0.082 라, `|κ| 0.5` 짜리 헤어핀도 0.041 로 환산돼
`LAT_ERR_KAPPA_LOW`(0.05) 아래로 떨어진다.

| `WINDOW_M` (decay 0.8) | 랩 |
|---|---|
| 1.0 / 2.0 / 3.0 | 7.59 s **전부 동일** |

→ 창을 키워서 보수적으로 만들려는 시도는 **decay 를 같이 키우지 않으면 무효다.**
이 상수는 `EXIT_DECAY_M = None` 으로 되돌렸을 때만 살아난다.

## 7. `LAT_ERR_CORNER_S` 를 내리는 절차

### 게이트 스윕 (라인 고정, 2026-08-09)

| corner_s | 프로파일 랩 | 폐루프 랩 | 게이트 | \|lat err\| max | 합성가속 (한계 8.83) |
|---|---|---|---|---|---|
| 0.117 (구값) | 8.45 | 8.70 | PASS | 0.180 | 8.19 |
| 0.105 | 8.01 | 8.30 | PASS | 0.206 | 8.22 |
| 0.095 | 7.70 | 8.03 | PASS | 0.229 | 8.22 |
| **0.090 ← 채택** | **7.59** | **7.93** | **PASS** | **0.234** | **8.26** |
| 0.085 | 7.48 | 7.85 | PASS | **0.292** ⚠ | **8.82** ⚠ |
| 0.075 | 7.38 | — | **FAIL** | 폐루프 벽 침범 5 step (t=6.68 s) | |

**0.090 = 백스톱 임계값(0.25) 아래인 마지막 칸.** 여유 6% (0.095 는 8%).
여기가 실질적 바닥이고, 더 내리려면 0.090 으로 달린 백을 아래 절차로
재측정한 근거가 있어야 한다.

> **0.085 는 게이트 PASS 여도 채택 금지.**
> `|lat err| max 0.292` 가 control 백스톱 임계값
> (`map/backstop_path_error_m = 0.25`)을 넘는다. 그대로 배포하면 헤어핀마다
> 백스톱이 speed 를 1.5 m/s 로 떨어뜨려, 없애려던 울컥거림을 CSV 가 아니라
> 런타임에서 다시 만든다. 합성가속도도 한계 0.01 앞이다.
> **게이트 PASS 만 보고 고르면 안 되는 값이다.**

### ⚠️ 순환 구조 — 한 번에 내리지 말 것

실측 slope 0.051 은 **"그 속도로 달렸을 때"** 의 값이다. 코너 `v_min` 이
2.58 → 3.18 (+23%) 되면 오차도 같이 커진다. 오차가 v² 로 는다고 가정해도
0.051 × 1.23 = 0.063 < 0.095 라 마진은 있지만, **한 칸 내릴 때마다 실차 백을
아래 방법으로 다시 재고 나서 그다음 칸으로 간다.**

### 재측정 방법

1. 새 CSV 로 실차 주행, 백 녹화 (`/pf/pose/odom`, `/odom` 필수)
2. `/pf/pose/odom` 을 CSV 웨이포인트에 최근접 투영 → 부호 있는 횡오차
3. `v > 1.0` 인 구간만, 출발·정지 구간 제외 (5 s 버킷으로 잘라 이상 구간 확인)
4. `build_map.recent_max_kappa()` 로 직전 곡률 계산 → 버킷별 `|lat err| / v` 의 **max**
   (p95 가 아니라 **max** 기준. 벽 충돌은 확률 문제가 아니다)
5. 그 값에 여유를 얹어 다음 `LAT_ERR_CORNER_S` 후보를 정하고 게이트 재실행

### 실행

```bash
cd planning_ws/src/planning_pkg/scripts/global_traj_sim

# 값을 시험만 해볼 때 (상수 안 고침)

# 확정하면 build_map.py 의 LAT_ERR_CORNER_S 를 고치고 근거 주석을 남긴 뒤
python3 build_map.py my_track0808
```

**주의:** `build_map.py` 는 `config/global_trajectory/` 의 배포 CSV 를 덮어쓴다
(실차가 읽는 파일). 게이트가 FAIL 하면 commit 하지 않으므로 안전하지만,
PASS 한 결과는 그대로 배포본이 된다.
